## 4. 🛠️ Claude Code & MCP ecosystem (community)

**The `.claude/skills` auto-load (v2.1.157) is the bigger architectural shift than the headline suggests.** Until yesterday, "plugin" meant marketplace publication, manifest, install step; "skill" meant a file in `.claude/skills/`. The two are now collapsing: any directory under `.claude/skills/` with a `SKILL.md` is treated as a plugin and gets the plugin lifecycle (autocomplete in `/plugin`, scaffolding via `claude plugin init`, recognizable by `claude plugin list`). For migration work this is the difference between a personal skill living in your dotfiles and a checked-in `.claude/skills/angular-modernize/` that the whole team gets for free on `git pull`. The check-in / autoload path is now first-class.

**[louislva/claude-peers-mcp](https://github.com/louislva/claude-peers-mcp)** — fresh MCP server letting multiple Claude Code instances on one machine discover each other and exchange messages via a localhost broker (SQLite + HTTP on `:7899`). Each session registers, polls once a second, gets cleaned up on exit. Optional gpt-5.4-nano summary of what each instance is working on (cwd + git branch + recent files) when `OPENAI_API_KEY` is set. The interesting bit isn't the chat — it's a usable substrate for *coordinating two long-running migration sessions* (one porting components, one running Playwright fix-loops) without baking it into a single dynamic workflow. Less heavyweight than `/workflows` for cases where you want two operators, not a hundred.

**[seclab-taskflow-agent](https://github.com/GitHubSecurityLab/seclab-taskflow-agent) — YAML-declarative agentic framework** on the OpenAI Agents SDK. Tasks are nodes in a YAML graph; the engine runs them, passes outputs forward, validates against Pydantic schemas, templates prompts with Jinja2. MCP-enabled, multi-agent. The companion [seclab-taskflows](https://github.com/GitHubSecurityLab/seclab-taskflows) repo separates the workflows from the engine — exactly the split your Spring Boot side would want for a curated set of internal "auth audit / dependency review / PII scan" workflows that lives next to the code. Concrete production result: ~30 fixed CVEs across OSS since August ([GitHub Security blog](https://github.blog/security/ai-supported-vulnerability-triage-with-the-github-security-lab-taskflow-agent/)).

**Telemetry escalation:** `OTEL_LOG_TOOL_DETAILS=1` in v2.1.157 now puts the actual bash commands and MCP/skill names into `tool_decision` OTel spans. If your platform team is anywhere near MRM/audit conversations on AI-in-engineering, this is the env-var to know — it's the first time the in-band tool-use telemetry has been verbose enough to drive a real audit trail without parsing logs.

## 8. 🎯 One thing to try today

**Upgrade to v2.1.158, flip Auto Mode on Bedrock/Vertex/Foundry, and check in your first auto-loaded `.claude/skills/` plugin.** Two-in-one — both are new today.

```bash
npm update -g @anthropic-ai/claude-code
claude --version   # confirm 2.1.158

# If your platform routes Claude Code through Bedrock (or Vertex/Foundry):
export CLAUDE_CODE_ENABLE_AUTO_MODE=1
# (Persist in your shell profile or, better, your team's Claude Code env config.)

# In the migration repo root, scaffold a plugin in .claude/skills/ (no marketplace):
claude plugin init angular-modernize
# Edit .claude/skills/angular-modernize/SKILL.md — the description field
# is the trigger spec (per Anthropic's skill-creator finding, cf 05-25 briefing).
git add .claude/skills/angular-modernize && git commit -m "skill: angular-modernize"
```

Why both at once: the Bedrock Auto Mode flip is meaningful only if you're going to *actually* run unattended sessions inside the regulated perimeter, and the auto-loaded skill is the cleanest way to make those sessions deterministic across the team (anyone who pulls `main` gets the same Angular-modernize behavior). Pair them and you've moved Claude Code one notch closer to "checked-in tooling" rather than "personal config." ~25 min.
