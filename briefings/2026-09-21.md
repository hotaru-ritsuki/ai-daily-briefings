## 4. 🛠️ Claude Code & MCP ecosystem (community deep dive)

- **`agent-native`'s "shared action" pattern is the interesting idea, not the framework.** Defining a capability once and handing the *same* typed action to both an agent (as a tool) and the UI (as a call) collapses the usual duplication where you write a REST endpoint and then re-describe it as an MCP tool. If you're building agent surfaces on top of a Spring Boot backend, the takeaway is portable: generate your MCP tool schema from the same contract your Angular services consume, so agent and UI can never drift.
- **Computer-Use as an MCP citizen.** `cua`'s framing of "Computer-Use 2.0" — the desktop exposed through **MCP/CLI to the agent you already run**, rather than a bespoke vision loop — is the pattern to watch. It means your existing Claude Code session can drive a sandboxed desktop as just another server, with `cua-fleet` orchestrating parallel sandboxes for eval/data-gen. Relevant if you want Playwright-style E2E but at the OS level.
- **Memory provenance is the next MCP hardening problem.** The attack-surface essay above lands as `cua`, `agent-native`, and ECC all ship *writable* memory. Practical hygiene for your setup: treat any server with write access to shared context (memory MCPs, notes, "instincts") as privileged, and don't co-mingle it with servers that ingest untrusted web content — that's the injection path.

## 8. 🎯 One thing to try today (≤30 min)

Clone Builder.io's **agent-native** and run the local quickstart to see the "shared action" pattern in your own stack (TypeScript, PGlite — no external DB needed):

```
git clone https://github.com/BuilderIO/agent-native && cd agent-native
```

Then follow the repo's quickstart to define one action and watch the *same* definition drive both a UI button and an agent tool call. The 30-minute question to answer: could your Angular services and a Spring Boot MCP tool share one action contract this way, instead of maintaining two? Even if you don't adopt the framework, the pattern is the takeaway.

**Draft:** Everyone's hardening skills and MCP servers, but the quieter risk is writable agent memory — persistent context that steers behavior and passes every byte-integrity check because the bytes are fine; it's the *provenance* that isn't. If a server can both read untrusted web content and write your agent's memory, you've built an injection channel.
