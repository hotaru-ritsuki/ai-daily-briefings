## 4. 🛠️ Claude Code & MCP ecosystem (community deep dive)

- **QM is the week's headline community harness ([`yc-software/qm`](https://github.com/yc-software/qm), MIT).** Where **OpenClaw** ([`openclaw/openclaw`](https://github.com/openclaw/openclaw), ~210k★) is a *personal* always-on assistant, QM is deliberately company-scale: triggers (crons/webhooks), shared files, connectors for a "company brain," agent-browser support, shareable web-app artifacts, and multi-player projects — with **model/harness swappable** (Claude Code, Codex, OpenCode, Pi) behind one core. The design lesson worth stealing even if I never deploy it: *scope memory, keychain, permissions, and sandbox per room*, not per user — that's the containment posture the containment disclosures (07-31) argued for, expressed as architecture.
- **MCP eval + discovery tooling is maturing past awesome-lists.** [`lastmile-ai/mcp-eval`](https://github.com/lastmile-ai/mcp-eval) exercises MCP servers in *real* LLM/agent environments instead of mocks — the missing piece for regression-testing the Spring Boot MCP servers I'm building against the new stateless spec. For discovery, [`tolkonepiu/best-of-mcp-servers`](https://github.com/tolkonepiu/best-of-mcp-servers) and [`RyanAlberts/best-of-Agent-Harnesses`](https://github.com/RyanAlberts/best-of-Agent-Harnesses) are *ranked, weekly-rescored* lists (the latter ships its own MCP + `llms.txt` so agents can query it) — a saner input than star-farmed catalogs.
- **The Playwright CLI is a context-engineering design pattern, not just a tool.** Its "write to disk, let the agent read what it needs" model is the same principle behind returning 1–2k-token subagent summaries instead of raw trails — but Ranger's data (§6a) is a useful reminder that fewer tokens ≠ automatically cheaper/faster, so measure before switching.
- **[`madebyaris/agent-orchestration`](https://github.com/madebyaris/agent-orchestration)** — an MCP server giving multiple agents shared memory, a task queue, and *resource locks* keyed off `AGENTS.md` workflows. The resource-lock idea is the interesting bit for parallel migration sweeps that touch overlapping files.

## 6. 📰 Articles & essays worth reading

### 6a. AI workflows & patterns

- **[The Hidden Cost of Fewer Tokens: Why context efficiency makes the Playwright CLI slower](https://outpost.ranger.net/post/the-hidden-cost-of-fewer-tokens/)** — *Ranger/Outpost*. Measures the assumption that fewer tokens = cheaper + faster: context efficiency held, but latency/cost gains largely didn't. *Takeaway:* stop treating token count as a proxy for run cost — instrument wall-clock and $ before swapping tools. ~8 min.
- **[The Context Wars: Why Your Browser Tools Are Bleeding Tokens](https://paddo.dev/blog/agent-browser-context-efficiency/)** — *paddo.dev*. First-hand breakdown of why streaming accessibility trees + screenshots into context is the real budget sink in agent browser automation. *Takeaway:* the "save to disk, read on demand" pattern generalizes to any high-volume tool output, not just browsers. ~7 min.
- **[AI browser automation token benchmark: Playwright CLI vs agent-browser vs Claude in Chrome](https://www.ytyng.com/en/blog/ai-browser-automation-tools-comparison-2026)** — *ytyng.com*. Head-to-head token counts (~22–24k CLI/agent-browser vs ~50k MCP) across identical scenarios. *Takeaway:* the numbers behind §1's rethink — useful baseline before I re-tool my Playwright agent flows. ~6 min.
- **[Spec-Driven Development in 2026: What It Is, the Tooling, and How Teams Actually Use It](https://dev.to/krlz/spec-driven-development-in-2026-what-it-is-the-tooling-and-how-teams-actually-use-it-2fk2)** — *dev.to/krlz*. Surveys the SDD tooling landscape (Spec Kit, Kiro, OpenSpec, Claude Code) and, more usefully, where specs-as-validation-gates actually hold vs. become ceremony. *Takeaway:* pairs with my verification-loops-as-skills work — the spec is the upstream gate, the eval skill is the downstream one. ~9 min.

## 8. 🎯 One thing to try today (≤30 min)

**A/B the Playwright CLI against your Playwright MCP on one real browser-automation task, and measure tokens *and* wall-clock — don't trust either number secondhand.** Pick one existing agent flow (e.g. "open the report page, assert the Highcharts widget rendered, screenshot") and run it both ways. Start here:

```
# docs + setup for the agent CLI:
https://playwright.dev/agent-cli/introduction
```

Run the same scenario through the MCP server you already have configured, then through the CLI, and log tokens consumed + seconds elapsed + $ for each. Ranger's whole point (§6a) is that the token win may *not* be a speed/cost win — so this is a 20-minute measurement, not a migration. If the CLI wins on my actual PDF/Highcharts test surface, it becomes the default tool for the Playwright subagents; if it doesn't, I've got hard data to stop chasing token-count as a proxy.
