## 4. 🛠️ Claude Code & MCP ecosystem (community, deep dive)

**The ecosystem's center of gravity this week shifted from *building* skills to *evaluating whether they trigger.*** As config size grows, the failure mode flips: a skill that produces great output is worthless if it never fires (false negative) or fires on the wrong prompt (false positive). Three concrete pieces:

- **[sjnims/cc-plugin-eval](https://github.com/sjnims/cc-plugin-eval)** (v0.4.0, TypeScript) runs a 4-stage loop: (1) parse the plugin and extract trigger phrases, (2) generate positive/negative/edge-case/paraphrase scenarios, (3) execute them against the Claude Agent SDK capturing tool interactions, (4) score which components fired — programmatic detection first (100% confidence from tool captures), LLM-judge as fallback. `npm install cc-plugin-eval`, then `cc-plugin-eval run -p ./plugin --dry-run` for a cost estimate before spending tokens.
- **[wshobson/agents](https://github.com/wshobson/agents)** added a three-layer `plugin-eval`: static analysis + LLM judge + Monte Carlo statistical reliability testing — the rigor angle if you want a *confidence interval* on trigger reliability, not a single pass/fail.
- **Anthropic's [skill-creator now tunes descriptions for triggering](https://claude.com/blog/improving-skill-creator-test-measure-and-refine-agent-skills)** — it scores a description against sample prompts and suggests edits that cut both false positives and false negatives. The headline finding (~50% baseline trigger accuracy when descriptions summarize rather than enumerate conditions) is the single most useful thing to internalize before writing your next `SKILL.md`.

[MLflow](https://mlflow.org/blog/evaluating-skills-mlflow/) and [LangChain](https://blog.langchain.com/evaluating-skills/) both shipped skill-eval harnesses on the same pattern (trace every action → run judges over the trace). The convergence is the signal: skill evaluation is becoming a standard pre-merge step, not a one-off.

**Discovery-surface data point:** [quemsah/awesome-claude-plugins](https://github.com/quemsah/awesome-claude-plugins) now indexes **18,424** plugin repos (as of May 24) via automated n8n adoption-metric crawls — useful as a *ranked-by-real-adoption* filter rather than the raw mega-dumps.

## 8. 🎯 One thing to try today (≤30 min)

**Run a trigger-eval against one real plugin/skill from your `.claude/` setup** — find out empirically whether it fires when you expect, before trusting it in an overnight migration run.

```bash
# 1. Install the eval framework
npm install -g cc-plugin-eval   # or: npx cc-plugin-eval ...

# 2. Point it at ONE plugin/skill directory and dry-run first (cost estimate,
#    no tokens spent):
cc-plugin-eval run -p ./.claude/plugins/<your-plugin> --dry-run

# 3. Run it for real — it generates positive/negative/paraphrase prompts,
#    executes against the Agent SDK, and reports which components triggered:
cc-plugin-eval run -p ./.claude/plugins/<your-plugin>
```

Pick a skill you *think* is reliable — e.g. a migration-specific `/code-review` or an Angular-modernize subagent. The interesting output is the **false-negative rate**: prompts that should have triggered it but didn't. If it's high, the fix is almost always rewriting the description to *enumerate trigger conditions* ("use when the user mentions AngularJS directives, `$scope.$watch`, or `.directive(`") rather than *describe behavior* ("reviews migrated code"). Re-run and watch the score move. That single calibration loop is worth more than adding three new skills.
