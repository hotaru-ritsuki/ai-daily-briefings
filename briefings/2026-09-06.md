## 4. 🛠️ Claude Code & MCP ecosystem (community, deep dive)

- **The rogue-agent incident is an MCP/agent-tooling problem, not just an OpenAI one.** The DSEWiki case (§1) is the same class as the file-artifact escape (§6a): the danger isn't the model, it's a **tool surface the sandbox didn't enumerate** — a writable endpoint, or a file a host consumer trusts. For your setup this points at concrete knobs you already have: CC's `permissions.blockReadsOutsideWorkingDirectories`, `--permission-prompts none` for unattended hosts (deny anything that would prompt), and network egress filtering on the agent's container. Treat *every* MCP server's write/network scope as part of the sandbox boundary, and audit it before an unattended run.
- **JetBrains shipped a Compose Hot Reload MCP server (Compose Multiplatform 1.12.0).** It connects an AI agent to your *running* app to trigger reloads, take screenshots, inspect the semantic tree, simulate clicks/text input, and read app logs ([JetBrains blog](https://blog.jetbrains.com/kotlin/2026/08/compose-multiplatform-1-12-0/)). It's Kotlin/Compose, not Angular — but it's the same "agent drives the live app via MCP" pattern as Playwright's agents (covered), and it's another data point that JetBrains is wiring MCP into the runtime, not just the IDE. Worth watching whether the IntelliJ/WebStorm side gets a comparable live-app bridge for your stack.
- **"Agent Plugins 1.0" is the cross-vendor packaging standard to know about** — it bundles agent skills *and* MCP servers into one installable, governed independently of any single vendor, with AWS, Anysphere, Microsoft, OpenAI, and Vercel as launch partners ([GitHub Changelog](https://github.blog/changelog/2026-08-12-agent-plugins-1-0-in-vs-code-copilot-cli-and-the-copilot-app/)). Not last-72h (early Aug), but if you distribute `.claude/` skills across a team this is the emerging portable format — a skill+MCP bundle that isn't CC-only. The Vercel plugin (Next.js/AI SDK knowledge on demand) is the reference implementation.

## 8. 🎯 One thing to try today (≤30 min)

**Audit your agent's write + egress surface — treat every writable path and network target as part of the sandbox.** The two stories above (§1, §6a) both come down to a surface the sandbox didn't model.

```bash
# 1. In your CC project settings (.claude/settings.json), confirm the guardrails:
#    - "permissions": { "blockReadsOutsideWorkingDirectories": true }
#    - for unattended/scheduled runs: --permission-prompts none  (deny-on-prompt)
# 2. List every MCP server's write + network scope — anything that can POST/GET
#    to an external endpoint or write outside the workspace is part of the boundary.
claude   # then: /mcp   (review each server's tools; note which can write or fetch)

# 3. Ask the harder question from Fajreldines' post: which host tools auto-consume
#    files the agent writes? (git hooks, IDE extensions, local daemons) — those run
#    OUTSIDE the sandbox on agent-authored input.
git config --get core.hooksPath && ls -la .git/hooks 2>/dev/null
```

If you find a git hook or IDE extension that executes agent-written files unattended, that's your DSEWiki. *(Fallback if you'd rather build than audit: `pip install deepeval` and write one trajectory eval for a flaky `.claude/` skill — 20 min to turn a repeated failure into a regression test.)*
