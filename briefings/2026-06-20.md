## 1. 🔥 Top 3 things I shouldn't miss today

- **"Harness engineering" has crystallized into a named discipline this week — worth adopting the vocabulary before your platform team reinvents it.** A constitutive definition paper ([*What makes a harness a harness*](https://arxiv.org/html/2606.10106v1)), LangChain's [*Anatomy of an Agent Harness*](https://www.langchain.com/blog/the-anatomy-of-an-agent-harness), Addy Osmani's [*Agent Harness Engineering*](https://addyosmani.com/blog/agent-harness-engineering/), and a fast-growing [`ai-boost/awesome-harness-engineering`](https://github.com/ai-boost/awesome-harness-engineering) (~1.9k★) all converge on the same four-part frame: **agent loop + tool interface + context management + control**. This is the precise vocabulary for the "why we run Claude Code *and* Codex behind one governed layer" argument you keep making — `Agent = Model + Harness`, and the harness (not the model) is what you actually control in a regulated shop.
- ⚡ **Anthropic published [*Demystifying evals for AI agents*](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) on its engineering blog** — task selection, trajectory-vs-outcome metrics, LLM-judge calibration, and **evals-as-CI**. For a financial-services migration where "did the agent change behavior?" is a compliance question, the eval-as-CI pattern is the artifact that turns your Playwright review-gate into something an MRM auditor recognizes. (Date hedged — see Run notes.)
- **Cognition's [FrontierCode benchmark](https://cognition.ai/blog/frontier-code) is the soundest-methodology coding benchmark in weeks, and the numbers are humbling**: it grades *mergeability* (correctness + test quality + scope discipline + style + codebase-standards) on tasks built with 20+ OSS maintainers across 36 repos (~40h expert work each). Best model — **Claude Opus 4.8 — scores just 13.4%** on the hard subset; GPT-5.5 6.3%, Gemini 3.1 Pro 4.7% ([StartupHub](https://www.startuphub.ai/ai-news/artificial-intelligence/2026/frontiercode-ai-coding-benchmark-goes-beyond-correctness)). The takeaway for the migration: agents pass functional tests long before they produce *mergeable* code — your human review gate is load-bearing, not theater.

## 8. 🎯 One thing to try today (≤30 min)

**Turn FrontierCode's mergeability rubric into a Claude Code reviewer-subagent scoring gate** — a concrete, low-friction way to make "is this migration PR actually mergeable?" a measured output rather than a vibe.

```bash
# 1. Confirm you're current (nothing to update today, just verify):
claude --version          # expect 2.1.183
codex --version           # expect 0.141.0

# 2. Drop a scoring rubric the reviewer subagent must fill in, mirroring
#    FrontierCode's five dimensions. .claude/agents/mergeability-review.md:
#    ---
#    name: mergeability-review
#    model: claude-opus-4-8
#    ---
#    Score the current diff 0–5 on EACH, with one-line justification + file:line:
#    1. Correctness (behavior preserved vs AngularJS original)
#    2. Test quality (Playwright/unit assertions are meaningful, not smoke)
#    3. Scope discipline (no orthogonal edits outside the target module)
#    4. Style (matches surrounding Angular 18 standalone + signals idiom)
#    5. Codebase-standards adherence (NgRx/RxJS conventions, OnPush)
#    Output a markdown table. Refuse to mark "mergeable" if any dimension < 3.

# 3. Run it on one migrated feature module and keep the table as the PR artifact:
#    claude -p "Use mergeability-review on the staged diff for
#               src/app/features/portfolio/. Output the score table only."
```

The payoff: a repeatable, documented review score (the MRM-friendly artifact from §7) and a sharp local data point on *how far* your agent output sits from mergeable — the gap FrontierCode shows is much bigger than functional-test pass rates suggest.
